# Value history and collection value are per-user, and count copies held

## Context and problem statement

Asked directly: is the collection's value computed per user, from the cards that
user owns? Half of it was.

**The "Collection value" tile was already right.** `app/(app)/layout.tsx` calls
`getCollection(viewer.userId)`, `lib/core/collection.ts` keys both its caches on
that id *and* passes it to the query, and `getCardsStats(sets)` sums over that
person's sets. The prices themselves come from the shared catalogue, which is
global on purpose — they are facts about cards, not about people.

**The "Value over time" chart under it was not.**
`app/components/CollectionValueCard.tsx` imported
`lib/core/collection-value.generated.json` — one committed file, generated by
`scripts/snapshot-collection-value.mjs` for one account — and
`CardsDashboard.tsx` rendered it unconditionally. Every signed-in account read
the seed owner's series: a new signup with three cards saw its own tile reading
"Collection value €12" with "Up €24,253 since December 2024, across 1,524 cards"
drawn directly underneath. `GET /api/v1/value-history` returned the same file to
any authenticated caller, including the iOS app. Wrong for the reader, and a
disclosure of one account's holdings to every other.

Two things surfaced while tracing it.

**The generator had been broken for everyone, not just for non-owners.**
`cardsFromBuild()` scraped the RSC flight payload of `${BASE}/cards`;
`app/cards/page.tsx` became a `redirect("/collection")`, `/collection` is behind
`proxy.ts`, and an unauthenticated fetch lands on `/login`. It found zero cards
and threw. Nobody had run it since.

**Neither the tile nor the series counted copies.** `cards-stats.ts` added
`shownPrice(card.price)` once per matched card and the script's `valueAt()`
folded a card's rows to one entry, so the per-variant `quantity` column added by
the 2026-08-14 inventory-fields migration was ignored in both. A card held three
times was valued as one.

### Why the committed file was reasonable once

`reconstructed: true`, `confidence: inferred`. No decision record covered value
history before this one; the reasoning below is read off the script's own header
comment, which argues the sourcing at length but was never written up as a
decision, so the *sourcing* is observed and the *storage* choice is inferred.

Nobody publishes this series. Cardmarket's API answers with today's price and no
history and is closed to new applications; TCGdex' free price-history repo is
TCGplayer in dollars, covers under half this collection, and stopped in June
2025. So the series cannot be fetched — it has to be recorded, and every run of
the script records one point. While there was one collection and no accounts, a
file in the repo was the cheapest possible place to keep three points, needed no
schema, and cost nothing at render time. What changed is not the sourcing but
that "the collection" stopped being one thing.

## Considered options

1. **Hide the chart for everyone but the seed owner.** Smallest change, closes
   the disclosure, leaves the data model and the broken script alone.
2. **A per-user snapshots table, a repaired generator, and a per-user API.** The
   series becomes data with an owner, like the cards it values.
3. **Recompute the history on the fly from `acquired_at` and today's prices.**
   No new table at all.
4. **Leave copies out of scope** and fix only the per-user question that was
   asked.

## Decision

We will do (2), and fix copies with it.

- `public.collection_value_snapshots` (migration `20260816140000`), one row per
  person per day, `unique (user_id, snapshot_date)`, with a single
  `using (user_id = auth.uid())` policy and **no public branch**.
- `getValueHistory(userId, token?)` in `lib/core/collection.ts`, cached per user
  under its own tag; `listValueSnapshots` in `lib/storage/postgres.ts` filters on
  `user_id` explicitly.
- `app/(app)/dashboard/page.tsx` becomes a server component that fetches the
  viewer's readings and passes them down; `CollectionValueCard` takes them as a
  prop and renders nothing below two points.
- `/api/v1/value-history` answers with the caller's own series, in the shape it
  always had.
- `copiesHeld()` in `lib/core/cards-stats.ts` multiplies the value tile, and
  `valueAt()` in the script multiplies the series the same way.

(3) was rejected on the grounds the script already argues: today's prices applied
to a 2024 binder is not what that binder was worth in 2024, and no free feed sells
the past. The history has to be recorded or it does not exist.

(1) was rejected because it leaves a real feature working for one account and
freezes a generator that had already stopped working, and because the disclosure
is the symptom rather than the defect — the defect is that a per-account number
was being kept somewhere that has no account.

(4) was rejected on Bart's answer when asked: *"alles wat nu data is, dat moet
gewoon per gebruiker dan soort van worden uitgerekend"*. A tile that says a
duplicate-heavy binder is worth what a single-copy one is worth is the same class
of untrue as a chart belonging to somebody else.

### Decisions inside the decision

- **No public branch on the policy.** `cards_read` has one, because
  `/user/<name>` cannot render a stranger's collection without it, and
  `stripPrices()` then removes the money card by card. A value series is nothing
  but money and, being an aggregate, cannot be partly stripped. `CardsView`
  already computes no stats at all on a public profile.
- **Cents in the table, whole euros above it.** The script's `Math.round` was a
  display choice that had become what the record remembered. Conversion happens
  in `listValueSnapshots`, so the v1 response shape never moved and the iOS
  client needs no change.
- **Its own cache tag, not `cardsTag(userId)`.** Adding a card does not add a
  reading, so sharing the tag would drop a still-correct cache on every edit; and
  the script writes from plain node, where `revalidateTag` does not exist, so it
  could not drop either tag anyway.
- **`getValueHistory` lives in `lib/core/collection.ts`, not a file of its own.**
  It was written as `lib/core/value-history.ts` first and the eslint cache leash
  refused it: two files may import `unstable_cache` so the move to `use cache`
  stays a two-file change. The rule was respected rather than widened. Only the
  `ValueSnapshot` type and the tag live apart, in `lib/core/value-snapshot.ts`,
  because `lib/storage/postgres.ts` has to name the shape it returns and would
  otherwise import the module that imports it.
- **"Priciest cards" stays ranked and priced per single copy**, unlike the value
  tile. It answers which cards are best, and ranking by stack value would list
  forty of a cheap common above a Charizard.
- **`priced` and `unpriced` stay counts of distinct cards.** They answer how much
  of a collection could be valued at all, which is coverage.
- **The generator asks the collection API instead of scraping a flight payload.**
  `--token <jwt>` for any account, the public endpoint for a public profile, and
  an explicit refusal otherwise. Card matching is emphatically not reimplemented —
  the endpoint returns the same `key`/`tcgId` objects the payload did.
- **No email/password flow in the script.** A token can be minted and discarded;
  a password in `.env.local` cannot.

## Consequences

- Good, because no account can see another's valuation, in the UI or through the
  API, and the wall is a row-level-security policy rather than a component that
  remembers to check.
- Good, because the generator works again, for any account rather than for one,
  and no longer needs a production build on port 3111 — `SITE` can point at a
  dev server or the deployment.
- Good, because the value tile and the chart now count the same thing, and
  `copiesHeld()` is one definition both read.
- Good, because a brand-new account sees no chart at all rather than a stranger's,
  and that is the existing "fewer than two readings" branch rather than new code.
- Bad, because **every account except the snapshotted one has no history and will
  have none until somebody runs the script for it.** Snapshotting is still manual
  and single-user-per-run. Nothing schedules it.
- Bad, because **the deprecated `x-cards-key` path now answers
  `{"snapshots":[]}`.** That header is a passcode, not an identity: it resolves to
  `OWNER_USER_ID` with no session, so `auth.uid()` is null and the policy
  correctly returns nothing. `/v1/collection` survives the same path only via
  `cards_read`'s public branch, which this table does not have. Accepted: the path
  already logs itself deprecated and the iOS app sends a bearer token.
- Bad, because **the collection value figure changes** the moment this ships — it
  rises by whatever the duplicates are worth. Historical points recomputed by a
  `--seed` run will not match the three in the old JSON file for the same reason.
  Expected, not a regression.
- Neutral, because a fresh reading can be up to an hour late on the dashboard.
  Nothing invalidates the cache — the script writes out of band — so the 3600s TTL
  is what buys freshness. `valueHistoryTag()` exists as the hook for the day there
  is a "snapshot now" button.
- Neutral, because `lib/core/collection-value.generated.json` is still in the tree
  and now imported by nothing. It is deliberately kept until a `--seed` run has
  reproduced its three points into the table: both historical points come from
  Internet Archive captures that are single points of failure, and that file is
  currently the only other copy of December 2024.

## Confirmation

- `lib/storage/postgres.test.ts` asserts `listValueSnapshots` names the user in
  the query, orders oldest first and converts cents — the same assertion the
  `listRows` block above it exists for, on the table where getting it wrong is
  worse.
- `app/api/v1/value-history/route.test.ts` asserts the route asks for the
  *viewer's* id with the viewer's own bearer, that two viewers get different
  answers, and that the `{snapshots: […]}` shape the iOS app parses has not moved.
- `lib/core/value-chart.test.ts` asserts that fewer than two readings draws
  nothing, which is the whole of "a new account sees no chart".
- `lib/core/cards-stats.test.ts` asserts the value multiplies by copies while
  `priced` and `top` do not.
- Not confirmed in a browser or against the real database: the RLS check (a
  second account seeing zero rows) and the two-accounts-side-by-side check both
  need live credentials and a signed-in session. Written down in `STATE.md` as
  the outstanding step, along with the `--seed` run.
