# The orb mark on the web — which cut goes where, and where the brand lives

## Context and problem statement

Card Orb had no picture of itself. Not "an old one" — none. No favicon, so every
tab showed the browser's blank page glyph. No `apple-touch-icon`. An `icons`
array in `app/manifest.ts` that was deliberately empty, with a comment saying why
and what it cost. A social card that was three lines of type on white. And the
word "Card Orb" set in the heading face, four times, in four files with the same
class string copied between them.

Meanwhile a complete set of assets had existed for a while in
`bartdunweg/cardorb-ios`, under `brand/` — 40 files, generated by
`Tools/GenerateAppIcon.swift`, with a `README.md` containing a section titled
**"Putting it on the website"** that names this repository, lists the three files
to copy and where to put them, and closes:

> These files are for hand-off: `cardorb.com` lives in the separate `cardorb`
> repository and does not pick them up automatically.

The hand-off never happened. Both halves of the gap were written down — the
README on one side, this in `app/manifest.ts` on the other:

> Put an `icons` array back the day this gets a mark of its own.

Two correct notes, in two repositories, describing each other, and nothing moved
for months. That is the actual problem this record is about. The asset copying is
the easy part.

## Decision

### The mark, and which cut

`brand/` ships two transparent cuts of the same sphere and one tiled version.
They are not interchangeable and the choice is per-context:

- **`orb-shadow-*`** — the sphere with its contact shadow. This is the wordmark's
  cut, at 24px, and the one on the social card. Both sit on a plain surface with
  nothing else giving them depth, which is what the shadow is for.
- **`orb-*`** — the sphere alone, filling its box. Shown on `/brand` and used
  nowhere in the product yet. It is the right answer where a layout already has
  depth or a shadow would fight it; nothing in the app is that today.
- **`orb-tile-*`** — the sphere on its off-white tile. This is `app/icon.png`,
  `app/apple-icon.png` and both manifest entries.

The last one is where the interesting decision is, because it goes against what
was asked for. Bart asked for the transparent cut, no background. It is the
transparent cut everywhere on a page. It is **not** for the favicon or the touch
icon, and the reason is not taste:

- iOS does not honour transparency in a home-screen icon. It composites the alpha
  channel onto black, so the transparent cut installs as a pale sphere in a black
  square — the one place the mark cannot be corrected after the fact.
- The orb is a light, glossy object. On Android and in a browser tab it is
  composited onto a background nobody here chooses, and a pale sphere on a pale
  wallpaper is not a logo, it is a smudge.

The tile is the same sphere and the same colours; it is the app icon, which is
what a home screen is being asked to show anyway. The transparent request is
honoured everywhere the background is known — which is every pixel of the site.

### Where the brand lives: split at the generator

There is a real question underneath this ("is this repo not the source of
truth?") and the answer is a split rather than a yes or a no:

- **The drawing is generated**, by `Tools/GenerateAppIcon.swift` in cardorb-ios.
  That generator is the origin, and it stays where the app icon it renders lives.
  A Swift toolchain has no business in a Next.js repository, and forking the
  render is how the site and the installed app would stop matching.
- **Everything downstream is here**: the served files, the colours, the usage
  rules. `/brand` is that page. This repository already serves `cardorb.com`,
  already holds the colours as code (`lib/design/tokens.ts`) and the name and
  tagline (`lib/core/config.ts`), and now holds the files under `public/brand/`.

The argument for writing the rules down *here*, rather than leaving the README to
carry them, is the months of nothing above: a hand-off that depends on a person
remembering to open another repository is not a hand-off. A URL is.

Consequence worth naming: those `/brand/…` paths are now a public contract, so
the filenames are fixed. That is the point of them — cardorb-ios can drop its
second copy of these files and link here for everything except the app icon,
which a bundle genuinely cannot fetch.

### Manifest icons come from `public/`, not from `app/icon.png`

The `icons` array names `/brand/orb-tile-192.png` and `/brand/orb-tile-512.png`,
not the routes that `app/icon.png` and `app/apple-icon.png` generate.

The empty-array comment this replaces was right about the failure mode — a
manifest pointing at icons that 404 is worse than one naming none, because
Android fetches both and fails the install. Hard-coding `/icon` would rebuild
exactly that risk: Next fingerprints those URLs in production, with the extra
cruelty of working perfectly in dev and failing only once deployed. `public/` is
served verbatim, so those two paths cannot drift.

### The social card keeps its words

`brand/og-image.png` is the orb centred on the tile colour, with no text, and the
README says as much — adding text is "a design decision for the site". The site's
card already carried the name, the headline and the short tagline, and a link
preview with a sentence in it beats a link preview with a sphere in it. So the
orb joins the existing card rather than replacing it, inlined as base64: Satori
has no filesystem, and an absolute URL would make the route fetch itself.

### One `Wordmark`, four call sites

The lockup is a component (`app/components/Wordmark.tsx`) before it is an image.
Four hand-copied class strings were survivable while the mark was a word; adding
an image to four copies is how the fifth one gets forgotten. `Navbar.tsx` already
made this argument for itself.

It is passed no `href` in `app/(app)/loading.tsx`, and that call site is
load-bearing rather than decorative: ADR-0046 established that the fallback may
only draw what is identical on every signed-in route, and the rail's head is one
of those things. Drawn as bare text there, the name would have slid left by the
width of the orb at the exact moment the page arrived — the class of jump
FB-0010 was reported for.

## Alternatives considered

1. **Copy the three files the README lists and stop.** The minimum, and it fixes
   the favicon. It leaves the wordmark as a word, leaves the rules in the other
   repository, and leaves the next person to rediscover all of this. Rejected:
   the missing icons were a symptom, not the problem.
2. **Move the generator into this repository.** Would make "SOT" unambiguous.
   Rejected: Swift in a Next.js repo, and the app icon would then be rendered
   somewhere other than where the app is built, which is how the two drift.
3. **Transparent cut for the favicon and touch icon too**, as literally asked.
   Rejected on the iOS black-composite behaviour above; the request is honoured
   everywhere the background is knowable.
4. **Replace the social card with `og-image.png`.** One fewer moving part and no
   base64. Rejected: it trades a preview that says what the product is for one
   that says only that it is round.
5. **`/brand` indexed, as a sixth public route.** Rejected: the root layout
   noindexes by default and five routes opt back in for reasons of their own.
   This is a hand-off page for somebody who already has the link. It is reachable
   from the marketing footer, which is deliberate — noindex and in no sitemap
   means that row is the only way to arrive at it.
6. **Reuse `LegalPage.tsx` for `/brand`**, which ADR-0042 asks be considered
   before adding a third long-form page. Its *type scale* is reused. Its shell is
   not: it requires an `updated` date this page has no use for, and caps its
   column at `--content-max` (~70 characters), which is right for a document to
   be read and wrong for a page whose subject is images side by side.

## Consequences

- Chrome on Android will now offer to install Card Orb, so `display: "standalone"`
  in the manifest stops applying only to hand-added home screen icons. That was
  the cost the old comment recorded, and it is paid off.
- `public/brand/` is ~850 KB of static assets. Deliberate: the larger cuts are
  AVIF-only for exactly this reason, and no 2048 PNG is hosted at all.
- `app/opengraph-image.tsx` now reads a file at module scope. It remains static —
  no data, no fetch, no `revalidate` — so this happens at build. ADR-0035 is the
  record on why static-versus-dynamic matters on that route specifically.
- The OG card's text column has an explicit `width: 700` rather than `flexGrow`.
  Satori sized the flexible column from its content, the 76px headline made it
  wider than the frame, and the orb was pushed off the right edge — a failure
  that looks, from outside, exactly like a card that never changed. Found by
  rendering it and looking at it; it would not have failed a build.
- Any new place that signs the product should use `<Wordmark />` rather than
  setting the name in type.
- cardorb-ios can now delete its committed copies of everything except
  `AppIcon.appiconset`. That is a separate change in that repository.
