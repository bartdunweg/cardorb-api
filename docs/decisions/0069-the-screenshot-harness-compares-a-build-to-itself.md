# The screenshot harness compares a build to itself, because its baselines are gitignored

**Read this before trusting a green `npm run visual`.**

## What was found

`.gitignore:15` ignores `visual/**/*-snapshots/`. The baseline PNGs are
therefore never committed and do not exist in a fresh checkout or a fresh
worktree.

Playwright's behaviour when a baseline is missing is to **write it and fail that
test**. So the first run in any workspace writes every baseline *from the build
under test* and reports a wall of failures; the second run passes, because it is
now comparing that build against pictures of itself.

Observed exactly, during this session's work:

    run 1, my build   33 failed   (baselines did not exist; Playwright wrote them)
    run 2, my build   35 passed   (compared against run 1's output)
    run 3, my build   35 passed

Three green runs, thirty-five passing screenshots, and **no regression signal of
any kind** — the harness could not have failed, whatever the change had been.

## Why this matters more than an ordinary bug

`STATE.md` treats this harness as the project's safety net, and says so
repeatedly: "every step before the chart was checked against thirty-three
screenshots", "Photographed and green", "The screenshots caught five regressions
that typecheck, lint and 525 tests all passed through", "**Do not trust a green
`verify.sh` on anything that moves a rule**".

The last of those is right, and the conclusion drawn from it was that the
screenshots were the thing to trust instead. In a workspace whose baselines were
generated by the same branch they are meant to police, they are not.

This is the fourth entry in a run of verification blind spots this repository has
now recorded — ADR-0018 (a class with more consumers than the obvious one),
ADR-0020 (a regression on a route needing a session), ADR-0066 (a vendored
component nothing had ever rendered), and this. Every one has the same shape: a
check that was believed to be running, and was not.

## Decision

**For any change that moves pixels, generate the baselines from the reference
commit, not from the branch.** Concretely, and this is what was done here:

    git worktree add /tmp/ref origin/main
    cp .env.local /tmp/ref/ && mkdir -p /tmp/ref/visual/.auth
    cp visual/.auth/owner.json /tmp/ref/visual/.auth/
    cd /tmp/ref && npm install && npx next build     # a symlinked node_modules
                                                     # fails: Turbopack rejects it
    npx next start -p <refport>
    VISUAL_BASE_URL=http://127.0.0.1:<refport> npx playwright test   # twice:
                                                     # run 1 writes, run 2 confirms
    cp -R /tmp/ref/visual/*-snapshots <this workspace>/visual/
    # then run the harness against your own build

Doing this turned three meaningless green runs into **fifteen real differences**,
each of which was then opened and accounted for.

**The baselines stay gitignored.** They are 33 PNGs of a real collection
rendered from a real session, they are large and they change with every
intentional visual change; committing them makes every design commit a binary
diff and puts a signed-in user's collection into the repository. The cost of
regenerating from a reference commit is a few minutes and is paid only by
changes that move pixels.

## What else this session learned about running it

- **The server must outlive the run, and proving that is part of the result.**
  It was killed mid-run three times here, each time producing a different and
  entirely fictitious failure list — including `ERR_CONNECTION_REFUSED` reported
  against a functional test that was fine. `STATE.md` already warns that a dead
  server photographs the app's own error boundary. **Curl the server after the
  run, not just before**, and discard any run it did not survive.
- **`maxDiffPixelRatio: 0.001` is generous for small glyphs.** Twelve 20px icons
  on a tall page are roughly 0.07% of it. An icon set can be swapped wholesale
  and stay under the threshold, so a green run is not evidence that icons are
  right; opening the picture is.
- `visual/.auth/owner.json` is gitignored too, so a reference worktree needs it
  copied in or its owner project silently does not run.

## Consequences

- Nothing in `STATE.md`'s history that claims screenshot verification can be
  relied on unless the baselines are known to have come from a different commit.
  The claims are not necessarily wrong — they are unevidenced, which by this
  repository's own standard is `not measured` rather than `pass`.
- `playwright.config.ts` and `.gitignore` are unchanged: the mechanism is fine,
  the assumption about it was not.

## Alternatives considered

- **Commit the baselines.** The straightforward fix, and rejected above on
  repository size, binary diffs, and putting a real signed-in collection into
  git. Worth revisiting if the harness ever runs in CI, where no reference build
  is available to generate from.
- **Fail instead of writing a missing baseline** (`--ignore-snapshots` or
  `updateSnapshots: 'none'`). Makes the trap loud rather than silent, and would
  have caught this. Not taken here only because it changes nothing about what a
  green run means once the baselines exist locally; the reference-commit habit
  above is the part that actually produces a signal. A good candidate for a
  follow-up.
